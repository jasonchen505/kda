# 简历与面试总结：本地大模型 Kernel Agent Harness

这个项目已经适合写入大模型算法／研究工程师简历，定位为有真实实验依据的
agent harness 原型。研究与工程对象是生成、修复、评测和选择 kernel 的 agent
闭环；六类 GPU 任务用于验证这个系统。不要把项目写成手工算子优化或完整 KDA
论文复现，也不要宣称已经验证通用生成成功率。

## 可直接使用的简历内容

**本地大模型 Kernel Agent Harness｜Python · Humanize/OpenCode · Qwen · Triton**

- 适配 KDA 的任务契约与草案工作流，搭建本地 Qwen 驱动的 kernel 生成闭环；实现
  结构化源码协议、分类失败反馈、受限修复上下文、预算停止和重复提案处理。
- 设计独立 GPU 数值与性能评测、源码 SHA 绑定、正确候选保留和新形状最终否决；
  从真实轨迹定位平均加速排序与性能门槛不一致的选择缺陷，修复为先满足门槛再排序。
- 实现任务级可恢复实验调度：原子检查点、单写者锁、不可变计划与累计预算预留；
  通过真实 SIGKILL 故障注入验证已完成结果复用、未知调用不重放及失败分母保留。
  故障测试使用真实 Humanize 流程及模拟模型／GPU 驱动，与生成成绩单独计数。
- 将共卡生成／数值验证与性能评测拆为独立阶段：原始候选按 SHA 进入持久化队列，
  测速可独立恢复；先冻结搜索选择再做最终检查。资源占用不会触发模型盲目修复，
  未完成测速不会计成性能成功。
- 完成等提案预算反馈对照和三任务真实生成验证；后者最终正确 3/3、性能晋升 2/3，
  SiLU/RMSNorm 在三种 BF16 形状下相对 torch.compile 平均加速 1.291×/1.073×。
  交付原始轨迹、冻结源码、离线证据校验与交互 HTML；结果限于该小样本实验配置。

版面只有两行时：

> 搭建本地 Qwen 驱动的 Triton Kernel Agent Harness，实现独立评测、分类修复、
> SHA 证据绑定和候选选择；完成同预算反馈对照，定位并修复选择器缺陷，交付可审计
> 实验报告。三任务集成验证最终正确 3/3、性能晋升 2/3。

## 三分钟面试叙述

我希望验证的是：一个 coding agent 怎样在数值和性能约束下可靠地迭代，而不是让
模型自己声称“优化成功”。KDA 提供了契约、草案与计划的工作流，Humanize 驱动实际
会话。我实现下游控制器，由外部评测进程裁决，每份源码都有哈希，错误转为分类反馈，
搜索阶段保留最好的正确候选，最后用不同形状检查并允许否决。

早期小模型经常生成错误 API 或格式不合法的代码。我把传输方式与源码表示分开做了
消融；逐行协议提高了基础源码准入，但没有把它说成 GPU 正确率提升。使用本地缓存
的较大模型后，我再固定同模型与三个提案机会比较有无实际反馈，两组都是 3/3 正确、
0/3 性能晋升，不能据此说反馈更好。

轨迹审计揭示了一个 harness 缺陷：平均值略高但最差形状严重回退的候选，被选在
满足性能门槛的候选前面。我改为门槛优先，用流程测试覆盖这个分支，并对两份固定
源码各做三次新进程重测。后续真实生成验证完成 3/3 正确、2/3 晋升，但推理服务配置
改变，而且第三轮后旧规则也选中同样结果，所以我没有把成绩归因于选择器修复。

项目价值是把 agent 的行为、失败和选择变得可以审查，同时展示了从负结果找到
控制器问题并修复的研究工程过程。随后我补了实验任务级恢复，用真实进程中断验证
完成结果不重跑、未知结果仍保留在分母中，预算也不会重置。六类任务、三种子、
两组反馈策略的 36 次运行已经终止 23 次，12 次最终正确、6 次晋升；8 次提前因
资源问题停止，另有一次最终检查因占用被否决，13 次待运行。这不能当成完整的
反馈收益对照，更不能将资源否决直接归因于模型能力。

这个瓶颈推动了下一项系统改进：生成和搜索数值验证可以共卡，原始模型源码进入
持久化测速队列；测量窗口出现后独立恢复，不需要再请求模型。搜索测速完成后
先冻结选择，再用最终形状检查。该模式只给模型数值反馈，因此以单独的集成试跑
验证，与原来的性能反馈实验分别计分。项目的下一步是完成对照、扩大未见任务与
引入 profiler 反馈，当前简历主线是已经实现和验证的控制器与评测工程。

本次共卡集成试跑完成 6 次真实模型提案，产生 3 份可测速的唯一源码；其余重复
提案复用原检查。GPU4 驻留其他进程时，3 份源码均通过 28 项搜索数值检查。
实际测速预检因占用返回待测，源码和预算记录没有丢失。该结果支持工程链路，
尚不支持这几份源码的最终正确性或性能收益。

## 面试时要能回答

| 问题 | 可以支持的回答 |
|---|---|
| 自己实现了什么？ | 下游控制器、评测与反馈契约、协议适配、候选选择、证据审计和报告；复用 Humanize/OpenCode 等组件。 |
| 2/3 是成功率吗？ | 是这次三任务单次运行的晋升数量，不能估计稳定成功率。 |
| 加速基线与口径？ | RTX 4090 上三种 BF16 形状，对 torch.compile，几何平均；另有最差形状门槛，不是端到端推理加速。 |
| 是否纯模型独立写代码？ | 使用官方 Triton 参考例子辅助；生成候选没有人工修改，不能宣称全新算法发现。 |
| 是否安全沙箱？ | AST 准入与独立进程是防错边界，尚未构成任意代码安全沙箱。 |
| 选择器修复提高多少？ | 固定候选重测支持缺陷与门槛一致性；新生成结果不能支持单独的因果提升数字。 |
| 中断后是否能完全恢复？ | 可以复用已提交的任务结果；任务内部的未知调用不自动重放，保留分母与预算。没有宣称 API 调用恰好一次或会话内部续跑。 |
| 共卡是否影响结论？ | 可以共卡生成和数值验证；它只产生待测速资格。性能评测独立排队，按原门槛选择后再做最终否决。当前 PID 边界检查仍是保守策略，不是硬件隔离。 |
