面向大模型算法／研究工程师。研究对象是写 kernel 的 agent 如何生成、修复与选择
候选；KDA、Humanize/OpenCode、Qwen、Triton 是复用组件。贡献在下游策略、控制器

## 前一轮：生成与修复的同起点交叉对照

新增两项可组合的 agent 策略：生成前在 draft/plan 中核对合约、输出坐标与内存偏移、
掩码和类型转换；修复时提供独立评测器产生的微型输入／预期／实际输出，结合失败
SHA 记忆与上下文允许时的正确版本锚点。源码仍由模型完整生成，没有人工修 kernel。

设计为 8 类任务 × 2 个新种子 × 2 种生成 × 2 种修复，**64/64 个最终结局已结束**。
32 个初始生成机会各执行一次，再把同一份源码和原始搜索裁决导入两种修复，每种
各两次机会；不是 64 个独立起点，也不是 192 次模型调用。实际派发 **152/160** 次。
所有组共享直连本地 Qwen 后端，去掉辅助标题调用，统一 8192 上下文与 2048 输出
额度。后端是公共实验设施，没有用旧 OpenCode 成绩计算因果加速倍数。

## 此前工程改进：在线反馈与可恢复的最终评测

上一轮的预算失败暴露了阶段边界问题：三个候选已搜到，但最终检查和额外审计仍
占用同一份 900 秒流程预算。新增 `search_only` 模式，保留在线数值与速度反馈，
先提交提案、原始搜索测量和固定选择；独立队列只验收选中源码，不重测搜索、
不将最终信息回传、不用最终数据重选。

新启动本地缓存 Qwen 27B FP8（GPU5/6），在 GPU4 运行转置与 Softmax 两项开发任务，
各三个提案机会。共 6 份原始提案、6 次独立搜索检查、5,325 个 SDK 输出 tokens。
搜索结果提交后，在最终评测子进程启动前真实 SIGKILL 调度进程；恢复复用 6 条
测量，仅执行 2 次最终检查，新增模型请求和搜索检查均为 0。再次打开已完成队列，
检查点和请求文件哈希不变。

| 任务 | 最终正确 | 最终平均 / 最差加速 | 性能门槛 |
|---|---|---|---|
| 转置 | 通过 | 0.979× / 0.957× | 未通过 |
| Softmax | 通过 | 1.257× / 1.014× | 通过 |

这轮支持阶段提交与恢复的工程实现，不能估计新版减少预算失败的概率，也没有

## 三分钟面试叙述

我想验证的是 coding agent 如何在数值、性能和预算约束下迭代。KDA 提供工作流，
Humanize 驱动会话；我实现外部控制器，由独立 GPU 进程裁决，每份源码都有哈希。
搜索阶段保留最佳正确候选，最终形状只接受或否决，不给模型继续修复。

最有用的发现来自负结果。原同预算反馈对照两组都是 3/3 正确、0/3 晋升。轨迹
审计发现平均排序会丢掉合格候选：平均 1.3366×、最差 0.773× 的源码压过了
平均 1.3354×、最差 0.998× 的源码。我改为门槛优先，用流程回归与两份固定源码
各三次新进程重测核对。后续三任务真实生成验证是 3/3 正确、2/3 晋升；它改变了
服务配置，不能把成绩单独归因于选择器修复。

下一项改进是实验恢复。任务开始前先落盘预算预留，提交时绑定结果与源码。真实
SIGKILL 测试证明已完成任务复用、未知调用不重放，预算不重置。测试使用实际
Humanize 流程与模拟模型／GPU 驱动，与生成成绩单独计数。

旧 36 次实验被设备调度卡住，停留在 23 次终止。我将生成与数值检查、持久化队列、
搜索测量和最终否决拆开。获得共卡授权后，已有 Softmax 候选通过独立测量计划，
以 0 次新生成请求完成五次 GPU 检查，两次最终正确且达到共享性能门槛。
随后独立完成六任务、两策略、12 次真实对照。无反馈 6/6 最终正确，反馈 5/6；
两组均 1/6 晋升。反馈组一次流程预算停止没有最终裁决，保留分母和实际源码。
这轮没有证明反馈收益，验证了控制、证据与预算停止链路。随后将在线反馈搜索
与最终验收拆开提交；在真实 Qwen 提案上验证最终阶段被杀后可以复用搜索并完成验收。

还有一个直观案例：向量加法选中候选的搜索平均／最差是 1.382×／0.997×，最终
只有 0.936×／0.812×。系统拒绝晋升，没有用最终数据重新选一个更好的版本。
项目的价值是把生成、失败、选择与中断变成可审查的研究工程过程。
