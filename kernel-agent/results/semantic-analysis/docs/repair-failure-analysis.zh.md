# 失败分析：有数值证据，仍然没有修对

正式实验中 `silu_mul-s20261102` 的合约生成初稿，在两种修复下都未被救回。
这是一个已封存的失败案例，不会通过人工改 kernel 或追加重试替换。
它不代表全部任务，但能具体说明“加入反例”与“修复有效”的区别。

## 证据链

契约要求 `SiLU(x) * y = x * sigmoid(x) * y`。模型初稿实现的是
`sigmoid(x) * y`，漏掉了乘数 `x`。微型探针第一项为：

| 项目 | 数值 |
|---|---:|
| x | 0.33333334 |
| y | 0.66666669 |
| 独立参考输出 | 0.12946007 |
| 初稿实际输出 | 0.38838014 |

普通修复的第一次修订重复了相同源码，第二次把 sigmoid 的写法改为 `tl.sigmoid`，
仍然漏乘 `x`。诊断反馈修复先把错误归因为 BF16 精度，尽管这个失败样本是 FP32；
第二次已经在文字中提到 `SiLU(x)=x*sigmoid(x)`，最终源码依然没有补回这一因子。
两种修复都没有产生搜索正确的候选，因此没有可以进入最终评测的源码。

## 对 agent 设计的含义

当前合约清单重视输出坐标、掩码和类型转换，不能替代算子数学语义的核对。
模型写出看似合理的故障假设，也不等于源码落实了这个假设。失败 SHA 记忆能发现
逐字重复，却不能把换变量名、换 API 但保留同一个语义错误的候选视为同一次失败。

这个案例支持的结论有限：当前提示与诊断上下文不足以保证修复成功。
它不能单独证明某种新架构更好，也不能据此改写整轮的策略效应。
本轮先完成并保留冻结对照的全部结果。

下一项可检验假设是：在同等调用预算内，先让一个独立审查步骤核对完整标量表达式、
全部输入和实际数值矛盾，再让生成步骤实现修复，是否优于连续重写完整 kernel。
这需要单独的新协议和对照；本次未将它作为已实现或已验证的收益。
