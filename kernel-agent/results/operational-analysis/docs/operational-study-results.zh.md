# 证据引导源码补丁：完成的同预算对照

本轮检验 kernel agent 的修复架构。改动由本地 Qwen 提出，控制器只机械应用、校验
和评测；没有人工修 kernel。22 个配对块、44 个最终结局、96/96 次物理模型调用
全部完成，96 份响应确认，基础设施故障为零。

## 结果与决定

| 独立分层 | 连续重写 | 证据引导补丁 | 条件性能门槛：重写／补丁 |
|---|---:|---:|---:|
| 已知失败回归：7 父源码 × 2 修复种子 | 7/14 | 9/14 | 2/14、2/14 |
| 新增四类任务 × 2 生成种子 | 7/8 | 6/8 | 1/8、1/8 |

均为独立最终正确数。回归的每份初稿在本轮重新评测，14/14 仍失败，全部调用完整，
因此救回也是 7/14 对 9/14。新任务两个初稿搜索正确；六个失败起点的条件救回为
重写 5/6、补丁 4/6，不能用它替代 8/组的最终分母。

按任务族等权的配对正确率差（补丁－重写）：

- 回归 +25.0 个百分点，探索性 95% 聚类区间 [−30.0, +70.0]，五个任务族。
- 新增任务 −12.5 个百分点，区间 [−37.5, 0.0]，四个任务族。

回归直接计数差是 +14.3 个百分点；它与 +25.0 的族等权估计权重不同。两个均保留，
不挑较大的作为“稳定提升”。种子、同父源码和每条补丁不是独立任务簇。新增任务由
项目自定义，属于前瞻验证，不能称外部盲测。没有把两个分层合并成一个成功率。

**保留普通生成＋普通修复为默认。** 新机制对目标旧失败有局部改善，但没有带来
新任务收益。支持的是“有限证据可帮助部分代码修复”，不支持广泛优于连续重写。
下一步优先验证更易生成的补丁表示或预算内完整源码回退，而不是继续加长数学解释。
本轮结束后没有追加重试、调参或替换失败结果。

## Agent 本身改了什么

1. 从两组独立搜索探针直接计算 expected/actual 与输入的简单数值关系；检测输入或
   输入乘积的有限排列，给出非方阵的坐标、平面偏移和唯一值对应。两探针都要满足，
   不查任务 ID 答案表。这些是有限样本提示，不是符号正确性证明。
2. 按真实编译／API／布局／数值失败分流，提供当前源码、错误和已安装 Triton 符号。
   双方共用 API 预检；本轮没有实际缺失符号命中，不能宣称它贡献了成功率。
3. 模型生成 1–4 处完整行前后替换，绑定当前源码 SHA。控制器拒绝过期、缺失、
   歧义、重叠、无效源码及无操作补丁，原子应用全部修改；不替模型修补回复。
4. 解析失败保留已准入源码，下一轮仍可修。正确候选由共同选择器保留；后续错误
   不会覆盖它。双方都提交选择后才访问最终样本，最终结果只能接受／否决。

这是表示、分流、证据和锚点共同改变的策略包，不是单组件消融。双方各两次修复调用，
每次输出上限 2048，无额外模型审查。生成模型、初稿、API 检查和 GPU 评测共同。
无初稿可用时，补丁组用原有调用槽恢复完整源码，没有额外机会。

## 修好了什么，为什么仍会退步

| 回归任务族 | 重写正确／计划 | 补丁正确／计划 |
|---|---:|---:|
| SiLU 乘法融合 | 0/2 | 2/2 |
| 转置（两个父源码） | 0/4 | 2/4 |
| RMSNorm | 1/2 | 2/2 |
| LayerNorm | 2/2 | 2/2 |
| 行均值（两个父源码） | 4/4 | 1/4 |

SiLU 的真实输出缺少输入因子。跨两探针的关系提示使模型在既有表达式上补回因子，
没有再改写成上一轮虚构的 `tl.expm1`。一个转置父源码也在两个种子都修好；另一个
父源码的四次补丁均被拒绝，没有“解释正确”就记成功。

行均值成为明显回退：模型仍误判累加器或除数，甚至把源码中不存在的 `width`
引入 JIT；一次删除输出偏移后仍写错位置。另有不匹配或无操作补丁。代码局部化并不
等于因果定位正确，正确数学片段也不能代替完整存储语义。

新增任务中列求和、仿射 SiLU 双方各 2/2；缩放转置双方 1/2；L2 归一化重写 2/2、
补丁 1/2。失败 L2 初稿把 torch.dtype 传入 Triton cast，补丁虽然描述了类型修复，
却在数组元素内塞入换行，第二次又包含无操作替换，被整笔拒绝。它说明协议的安全
校验正确执行，但过重的输出约束会直接降低 agent 的有效修复机会。

## 协议成本与实际资源

补丁组 44 次调用中，2 次为无初稿的完整源码恢复，42 次为补丁。25 次精确应用，
17 次拒绝，拒绝占 40.5%。拒绝原因：12 次不唯一／不匹配／无操作，4 次一元素
多行，1 次截断 JSON。应用不保证数值正确。六次首补丁拒绝之后仍有第二次机会，
其中两次成功修好并最终通过，其余四次未救回。它们不是额外试验。

实际输出总计 48,929 tokens：共同新初稿 7,561、重写 23,387、补丁组 17,981。
调用数为共同初稿 8、两组各 44。196,608 是额度，不是实测用量；补丁组输出较少
不等于更高成功率或端到端加速。92 份回复 stop、4 份 length，失败均保留。

三路服务分别分配 6、9、7 个块；真实请求峰值并发三个端口。107 个独立 GPU 窗口
峰值重叠一，27 份独立最终源码评测。GPU4 共卡被允许，速度仅是当时相对
`torch.compile` 的条件比值。未测 LLM 端到端吞吐加速，不推断跨缓存权重完全相同。
