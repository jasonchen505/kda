# Prospective RTX4090 multi-stage workflow transfer study

The user explicitly reopened multi-stage work after portfolio closeout. This is a new
4090 port, not a B200/FlashInfer contest reproduction or a change to Humanize upstream.
Freeze this protocol and all executed sources before study calls. New raw evidence stays
under remote `kernel-agent-storage/experiments/`; Mac/Git receive core code and compact summaries.

## Questions and arms

1. Can KDA's separated investigation/planning, tool-directed implementation, fresh evidence
   review, profiling and shape analysis run on the present local-model/4090 stack?
2. Does adding this project's source-grounded feedback and indexed repair to that staged
   workflow improve final acceptance on these development tasks, and at what cost?

Three arms run from scratch, no shared generated parent:

- `fixed`: ordinary full-source generation/feedback in the existing controller style;
  at most six candidate proposals, automatically evaluated. It is an extended local
  controller baseline, NOT original KDA or the old frozen three-proposal experiment.
- `staged`: three stages (research/correctness, profiler refinement, shape tuning). Each
  starts with separately persisted draft and executable-plan calls. A writer chooses real
  hosted read/research/submit/evaluate/profile/finish tools; a fresh reviewer cites actual
  event ids and is subject to deterministic stage requirements. Full-source proposals.
- `staged_transfer`: same staged architecture, plus existing finite numerical/coordinate
  interpretation, partial source facts, SHA-indexed patches and full-source submission
  fallback within the same opportunity budget. No automatic code repair.

All use the real Humanize SDK at the pinned d7f732e9 source and its real LiteLLM backend,
through a loopback audited gateway to an explicitly authorized local Qwen replica. Native
CLI/shell tools are not granted. The model chooses hosted tools; this is genuine but
bounded tool autonomy, not arbitrary repository/shell exploration or the original RLCR
plugin. Reviewer uses a fresh context on the SAME model process; error independence is
not established. All three roles' requests, not only source generations, count.

## Design and resources

Three previously developed families: affine-SiLU (pointwise), scale-transpose (index/layout),
L2 normalization (reduction). First-port feasibility cohort: ONE new seed, 2026101701,
three paired blocks/nine arm outcomes. Before freezing or efficacy calls, scope is deliberately
limited from a draft two-seed design to one seed: prove integration and expose costs first,
not a large statistical strategy study. Randomized block and arm order; each block pinned to one process identity.
Three idle authorized services scheduled using the existing unused-first/EWMA policy.
No paid model API; no restart of foreign services. Cross-root weight equality remains
unverified. Family count is three, not eighteen independent task families.

Common ceilings per arm: 24 model opportunities, input+2048 reserved output <=8192 tokens,
temperature .2, at most six submissions (rejected submissions consume an opportunity),
nine search evaluations, two profiler tools, one selected-source final evaluation. Maximum
216 physical model dispatches/442368 reserved output tokens for the entire study. Fixed
policy normally uses six calls, leaving its unused planning/tool budget unspent. These are
equal ceilings, NOT equal actual inference cost or equal information access. Report actual
calls, input/output tokens, candidates, tool time, elapsed time, and stage results. The
workflow comparison is a bundled intervention, not an isolated causal planning effect.

Each staged phase allows two planning calls and at most two reviews. Research allows six
writer actions, later phases four, all inside the same24-call total. A failed phase blocks
advancement: no profiling-refinement label is granted before research acceptance, and no
shape phase runs before profiling-phase acceptance. This is a strict gate, not an advisory
review score. A failed reviewer is never replaced with invented acceptance. Actual GPU
search correctness is required for all accepted stages; profiler stage additionally needs
successful source-bound counters or explicitly degraded CUDA activity; shape stage needs
actual three-shape measurements on two distinct correct source variants, not repeated tests
of one source. Missing hardware counters must remain an explicit limitation.
Final numerical/performance acceptance remains authoritative even if a reviewer disagrees.
Passing a stage is not proof that its optimization improved performance.

CUDA evaluation uses the existing GPU4 serialized, UUID-verified independent evaluator.
Sharing is allowed. Timing ratios are conditional. Nsight Compute 2024.1.1 is used for
candidate-only ranges, not the obsolete default ncu2021 binary. Save original .ncu-rep,
CSV/text, metric values, physical device identity and errors. Failed profiling is an explicit
blocker, never relabeled as valid diagnosis. Preflight-v2 confirmed NCU ERR_NVGPUCTRPERM.
Before efficacy calls, add the same CUDA-activity fallback to both staged arms: retain NCU
failure, collect real torch.profiler kernel/launch durations and Chrome trace; label status
`profiled_activity`, not successful NCU. The phase may accept this degraded activity evidence
with an explicit missing-counter limitation. It cannot claim measured SM/DRAM/stall
bottlenecks. This information downgrade is a transfer result, not restoration of full KDA
profiler fidelity. No server permissions are changed. Keep Blackwell-only recipes out of Ada code.
Pinned KernelWiki retrieval reports its architecture limits; official Triton3.2 examples
and API cards are available through tools. Fixed controller receives its existing reference
context. No old generated solution or public final contest answer enters fresh generation.

## Integrity, preflight and outcomes

Use a separate remote runtime cloned from the controller environment, adding LiteLLM;
record its installed requirements SHA and package versions without mutating old runtimes.
The gateway refuses duplicate SDK tickets/retries and persists allocations and exact wire
requests before dispatch. Unknown calls are not replayed. Context/policy failure is local
to its arm. A confirmed unknown external request quarantines that gateway; do not retry it.
An interrupted block is terminal unknown on supervisor restart, not resumed model work.

All three arms commit search-only selection BEFORE any final workload is read. The final
result is accept/veto only, absent from all model prompts, with no reselection. An arm
without a correct selection stays in the denominator. Keep deployment/smoke data separate.

Before study: meaningful mechanism tests and lint; three-service real SDK smoke; one
explicitly HANDWRITTEN profiler capability fixture, excluded from agent scores. Initial
preflight-v1 returned a typed but semantically wrong ready reply; it remains archived.
Clarified role instructions and later preflights are integration work, not efficacy data.
V4 checks all three real SDK role schemas. An unscored pilot exposed dropped rejected-source
context and advisory phase advancement. Before scored calls, preserve exact rejected source
in all arms and make stage transitions strict. The zero-dispatch prepared v1 ledger is kept;
the final source/protocol use a fresh scored-study directory. Do not pool the pilot.
The pilot also overflowed mandatory context by repeating old tensor evidence. Before scored
calls, all arms preserve the complete latest source, latest verdict and one exact finite
search witness; older events appear as an id/status index, not repeated full tensors. Added
source facts/derived hints remain optional and actual tokenizer counts decide omissions.
This is a new role-aware bounded-context port; no failed pilot ledger is repaired in place.

Primary descriptive endpoints: final correctness/3 per arm, final performance promotion/3,
paired differences by task/seed, actual resource costs. Report accepted/attempted phases,
review rejection/unsupported claims, chosen tool traces, profiler success and any fallback.
Do not pool old repair studies into this cohort. No broad generalization, statistical
significance, universal autonomy or superiority over original KDA claims. If the first port
fails, retain failure paths and distinguish missing orchestration from a policy null result.
