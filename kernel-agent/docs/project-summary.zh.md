# 本地大模型 Kernel Agent Harness：简历与面试总结

面向大模型算法／研究工程师，研究写 kernel 的 agent 如何生成、修复、选择和验收
候选。参考 KDA 方法，复用 Humanize 的执行能力，在下游实现独立评测、可信反馈、
预算修复、资源调度和实验审计；没有改造 Humanize 核心。

新增 4090 移植版在真实 Humanize SDK 上运行独立草案／计划、模型选工具和证据审查，
复用本项目的预算与验收机制。它是受限工具、同模型新会话的多阶段实现；没有等价复现
原 Claude／Codex 插件长会话或 B200 比赛环境。见[移植结果与成本](staged-results.zh.md)、
[原流程与收口时路线的历史比较](workflow-comparison.zh.md)。普通修复仍为默认配置。

## 简历可用表述

- 参考 KDA，在 RTX4090／本地 Qwen 上实现真实 Humanize SDK 多阶段 Kernel Agent：独立规划、模型选工具、证据审查；自主实现独立 GPU 评测、预算修复、搜索选择与最终否决，候选不经人工修补。
- 设计可信数值／坐标提示、SHA行号补丁与预算内回退。上一轮同初稿三组对照中，已知
  失败回归13/14，对照重写9/14、文本补丁7/14；近期新生成三组均6/8。进一步加入源码
  签名／调用／存储事实，历史八族新生成8/8，行号对照7/8，仅一个新种子，公开适用范围。
- 实现按实际提示分词的上下文适配、策略故障隔离、三路Qwen空闲准入／EWMA调度和
  GPU4共卡串行验收；236项工程检查通过，预算与隔离独立验证为24/24次实际派发。

默认保留，新机制不因实现完成或局部点估计上升就自动晋升。

## 三分钟面试叙述

我研究的是coding agent怎样在数值、性能和资源约束下可靠迭代。Qwen提出源码，控制器
记录SHA、父子关系和调用预算，独立GPU进程裁决。搜索反馈可以修复；所有选择提交后，
最终检查只验收或否决，不回传模型或用于重选。

最早的真实失败揭示了选择器问题：只比平均速度会丢掉满足最差形状门槛的候选。我修复
排序，保留旧失败，再分别用固定源码重测和新生成路径验证。工程上补了持久化预算与
阶段提交；真实SIGKILL后复用已提交结果，未知外部调用不重放。

提示策略也出现过退步和空结果。于是把可信数值／坐标证据直接接入源码补丁，再从协议
拒绝找到行号表示与预算内回退的机会。它改善了已知失败回归，却没有带来近期新生成
净收益，所以我没有把回归成绩写成普适成功率。

上一轮加入源码签名、调用绑定和存储依赖，初轮新生成为8/8对7/8。同时发现两个回归块
被新反馈挤爆上下文，还错误地取消了对照。这个问题属于harness，不能归咎于外部GPU。
我保留原账本，增加首次可容纳视图选择和策略隔离，再用两个新种子独立验证，结果为
5/6对3/6。这轮最重要的工程成果是让新增策略不能破坏对照与预算边界。

## 面试追问

| 问题 | 可支持的回答 |
|---|---|
| 自己实现什么？ | 下游修复接口、可信反馈、独立评测与选择、持久化预算、恢复、多服务调度和证据重建；上游组件明确复用。 |
| 与完整 KDA 有什么差别？ | 原 KDA 使用真实仓库工具、Claude／Codex 插件长会话和 B200 工作负载；新增移植版有三阶段接线，但使用本地 Qwen 新会话、宿主记忆、受限工具和 CUDA 活动降级；真实阶段完成按实验单独报告。 |
| 近期实验还用 Humanize 吗？ | 早期用 SDK／OpenCode，中期对照直连 Qwen；新增多阶段版真实使用 SDK／LiteLLM／审计网关。不把不同路线称为同一次执行或后端因果对照。 |
| 为什么同调用数还报告成本？ | 源码事实增加上下文；初轮两组各24个真实修复调用，新策略输入tokens增加14.1%。 |
| 语义检查保证正确吗？ | AST、Python编译和有限探针都不能证明任意Triton正确；源码事实是部分观察，仍需独立GPU数值验收。 |
| 预算失败如何处理？ | 实际请求先分词，完整／压缩／原对照视图依次选择；共同源码与数值证据不截断。上下文拒绝只影响本策略。 |
| 恢复与共卡边界？ | 任务／阶段提交点恢复，未知调用不重放；三路生成与本项目GPU4验收串行分离，其他用户允许共卡，性能是条件观察。 |
| 尚未证明什么？ | 完整KernelBench、外部盲测泛化、端到端推理加速、任意代码安全沙箱或模型训练收益。 |

## 新增多阶段版的面试案例

修正轮九个结局、99次确认调用：固定闭环3/3正确（18次调用），基础多阶段2/3
（41次），经验增强2/3（40次），均无性能晋升。完整三阶段通过0/6；两组各通过两个
研究阶段。源码事实进入15次实际请求，补丁调用0次。结果不支持把多阶段版升为默认。

分阶段并没有自动带来收益。第一轮 reviewer 把后续形状要求带入研究阶段，又看不到读取／
检索事件。我保留九个失败／成功结局，另用新种子修正阶段接口并重新对照。模型现在
可以通过部分研究阶段，但规划仍可能超出行动预算、使用不存在的工具、要求拿不到的
硬件指标。结论按最终正确、阶段完成和实际成本分别给出；不把合成三阶段通关测试
写成模型通关，也不把修复工具可用写成修复效果已验证。
